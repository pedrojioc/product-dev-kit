# Domain design

## Aggregate
- Consistency boundary: inside changes atomically; outside is eventually consistent. One root; outsiders hold only the root and reference other aggregates by id.
- Keep small. A child entity goes inside only if it cannot exist without the root, must be consistent immediately, and is loaded with the root. Otherwise it is its own aggregate referenced by id.
- One mutation style: in-place. The root is a class extending `AggregateRoot` with a private constructor, `readonly` identity, private fields behind getters, and NO public setters. State changes only through behavior methods returning `void` (`animal.exit(reason, occurredOn)`); each enforces the invariants and records events.
- One creation style: a named static factory taking one input object (`register`, `enroll`, `fromFarrowing`). Never `new` from outside.
- One use case saves exactly one aggregate. Effects on another aggregate run in a subscriber reacting to an event, never two saves in one use case.
- Behavior lives on the aggregate, not in services. Tell, don't ask.
- Time is data: commands carry the business date (`occurredOn`); the technical timestamp (`recordedAt`) comes from the `Clock` port. Never `new Date()` in domain or application.

## Value object
- Immutable, compared by value, self-validating: no code path builds an invalid instance. Operations return new instances.
- Wrap every concept with a rule or meaning (ids, tags, parity, ranges), including compound records and method-parameter shapes; a bare string-literal union with no validation is primitive obsession.
- Single-value VO: `class AnimalTag extends StringValueObject`, public constructor validates then calls `super`. Ids: `class AnimalId extends Uuid`. Composite VO: private constructor plus static factories (`Parity.declared()`, `FarrowingOutcome.of()`).
- File is a flat sibling of its aggregate in `domain/`. No per-aggregate `value-objects/` folder, no `.vo.ts`. Only the project-wide base classes live in `shared/domain/value-objects/`.
- `Uuid` accepts only UUID v7 (time-ordered): validate version nibble 7 and RFC variant. Ids are generated by the `IdGenerator` port (v7), never inside the domain.

## Invariants and errors
- Three exceptions in `shared/domain/exceptions/`, each `<name>.exception.ts`: `InvalidValueObjectException` (invalid data; VO or entity validating its own fields, HTTP 400), `BusinessRuleViolationException` (valid data breaking a rule or illegal transition; aggregate method, 422), `NotFoundException` (404).
- `NotFoundException` and every precondition needing data the entity cannot see are thrown by the application layer, never by an entity or aggregate.
- Never plain `Error`, never framework or HTTP errors in domain. The message carries the offending value.

## Domain events
- Past tense, one per business fact, immutable, a class implementing `DomainEvent { eventName, occurredAt }` in `domain/` (`farrowing-recorded.ts`). It may carry VOs. Raised by the root via `this.record(...)`.
- The use case saves, then `pullDomainEvents()`. Domain events never leave the module: the application maps them to integration events (see use-cases.md).
- Subscribers (application layer) translate the foreign payload to local types on receipt and are idempotent by business key.

## Policies and domain services
- Swappable rules are an abstract class in `domain/` (`CategoryPolicy`) with a default implementation selected in the composition root.
- Domain service only for logic spanning aggregates that belongs to none: stateless, pure, no repository or port access; application loads data and passes it in. Not a place for CRUD wrappers or `*Service` god classes.

## Append-only history
Recorded facts are immutable: closed cycles and records are kept as immutable VOs; corrections exist only if a spec adds them.
